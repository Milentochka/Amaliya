# Модуль 1. Регистрация и личный кабинет

## 1. Цель
Единая система авторизации для всего проекта. Гости входят по паре «Имя + Дата рождения» (без пароля). Админ — по логину и паролю. После входа гость попадает в свой личный кабинет, где собрана вся персональная информация по модулям 3, 4, 5 и информация о мероприятии (модуль 2).

## 2. Роли пользователей

| Роль | Авторизация | Возможности | Аватар |
|------|-------------|-------------|--------|
| **Гость** | Имя + ДР | ЛК, бронирование подарков (модуль 3), участие в конкурсах (модули 4, 5), просмотр информации о мероприятии (модуль 2) | Авто-присвоение из набора (см. §8) |
| **Админ** (родители — мама и папа, по аккаунту на каждого, равные права) | Логин + пароль | Управление гостями (создание/редактирование/удаление), управление контентом всех модулей, доступ к статусам и результатам, режим ведущего на банкете (см. `module4-spec.md`) | **Мама → Котёнок по имени Гав** (#49); **папа → Бонифаций** (#51) — закреплены, не меняются |

## 3. Профиль гостя

### 3.1. Поля профиля

| Поле | Тип | Обязательность | Заполняется | Редактируется гостем | Используется как |
|------|-----|----------------|-------------|----------------------|------------------|
| Имя | Строка | Обязательное | При регистрации (или админом) | ❌ | Часть логина, отображение, обращение бота |
| Дата рождения | Дата `ДД/ММ/ГГ` | Обязательное | При регистрации (или админом) | ❌ | Часть логина, расчёт зодиака и года животного |
| Пол | Перечисление: М / Ж | Обязательное | При регистрации (или админом) | ❌ (только админ) | Обращение бота («господин» / «госпожа») |
| Аватар | Сказочный герой из набора | Обязательное | Авто-присвоение | ❌ | Визуальная идентификация в списках |
| Telegram-ник | Строка | Опциональное | Через привязку бота | ✅ (привязать/отвязать) | Канал для уведомлений |
| Знак зодиака | Производное от ДР | Авто | Авто | ❌ | Отображение, использование в конкурсах |
| Год животного (китайский) | Производное от ДР | Авто | Авто | ❌ | Отображение |

### 3.2. Формат и валидация даты рождения
- **Формат ввода:** `ДД/ММ/ГГ` (маска ввода в форме)
- **Допустимый диапазон:** 01.01.1940 — сегодняшняя дата
- **Правило интерпретации 2-значного года:**
  - `00–26` → `2000–2026`
  - `27–39` → отвергается (вне диапазона)
  - `40–99` → `1940–1999`
- **Ошибка валидации:** при дате вне диапазона форма показывает «Дата вне допустимого диапазона».

### 3.3. Уникальность гостя
- Уникальной является пара **(Имя + ДР)**.
- В админских списках ДР отображается рядом с именем для различения дублей.
- В гостевых списках (на странице мероприятия, в виш-листе и т.д.) ДР скрыта; различение визуально — через сказочного героя (он уникален).

## 4. Регистрация и вход гостя

### 4.1. Единая форма «Имя + ДР + Пол + RSVP»
- Гость попадает на сайт по публичной ссылке.
- Видит **одну форму** с пятью обязательными полями:
  1. Имя
  2. Дата рождения (`ДД/ММ/ГГ`)
  3. Пол (М / Ж)
  4. **RSVP-Крестины** (Приду / Не приду / Возможно)
  5. **RSVP-Банкет** (Приду / Не приду / Возможно)
- Алгоритм:
  1. Гость заполняет форму.
  2. Система ищет в БД пару (Имя, ДР):
     - **Найдена** → авторизация в существующий аккаунт. Поля «Пол», «RSVP-Крестины», «RSVP-Банкет» при этом игнорируются (берутся текущие из БД); гость может изменить их позже в ЛК.
     - **Не найдена** → создаётся новый аккаунт с введёнными данными, авто-присваивается аватар, создаются 2 записи в таблице `rsvp` (см. `module2-spec.md`), гость авторизуется.
- Длительность сессии гостя: **30 дней**.

> RSVP-поля собираются в форме регистрации, но хранятся в отдельной таблице `rsvp` (детали — в `module2-spec.md`, разделы 5 и 9). Профильные поля гостя (раздел 3.1) — это только Имя, ДР, Пол, аватар и Telegram.

### 4.2. Авто-присвоение аватара
- При создании нового аккаунта система выбирает **случайно** из ещё не занятых героев.
- **Котёнок по имени Гав (#49) и Бонифаций (#51) исключены из пула для гостей** — они закреплены за админами (мамой и папой).
- Гостям доступны **49 героев** (из 51 в каталоге).
- Если все 49 заняты — регистрация блокируется с сообщением «Все слоты заняты, обратись к админу».

### 4.3. Привязка Telegram (опционально, через ЛК после входа)
- В ЛК отдельный блок «Telegram».
- Если ник не привязан — кнопка «Привязать Telegram». При нажатии:
  1. Система генерирует уникальный код.
  2. Показывает гостю команду вида `/start <код>` и ссылку на бота `t.me/<имя_бота>`.
  3. Гость открывает бота, пишет команду — бот привязывает его Telegram-аккаунт к профилю.
- Если ник привязан — кнопка «Отвязать».

## 5. Авторизация админа

- **Два аккаунта** (мама и папа), создаются при инициализации системы (через миграцию или CLI-команду на бэке). Оба админа имеют **равные права**.
- У каждого свой логин и пароль; пароль хранится в виде хэша (argon2).
- Вход через отдельную форму `/admin/login`.
- Сессия админа: **30 дней** (cookie с подписанным JWT или серверная сессия).
- Привязка Telegram у каждого админа — через тот же механизм, что у гостя (`/start <код>`). Все TG-уведомления (бронирования, видео на модерацию, RSVP, изменения и т.д.) отправляются **обоим** админам.
- В админке админ может **создавать, редактировать, удалять** любого гостя (см. §6).
- На банкете любой из двух админов может включить **режим ведущего** для проведения конкурсов модуля 4. Конфликты — last-write-wins (см. `module4-spec.md`, §2.2).

## 6. Управление гостями (для админа)

### 6.1. Создание гостя вручную
- Админ заполняет форму: Имя + ДР + Пол.
- Система проверяет уникальность пары (Имя, ДР):
  - Если такой пары нет — создаётся новый аккаунт, авто-присваивается аватар.
  - Если такая пара уже есть — операция отвергается (нельзя создать дубль).

### 6.2. Редактирование гостя
- Админ может изменить любое поле гостя: Имя, ДР, Пол, аватар, Telegram-привязку.
- При изменении (Имя или ДР) система проверяет, что новая пара (Имя, ДР) не пересекается с другим гостем.

### 6.3. Удаление гостя
- Админ может удалить гостя.
- При удалении: освобождается аватар, отменяются все бронирования гостя, ответы в конкурсах архивируются (не удаляются физически), Telegram-привязка снимается.

### 6.4. Коллизия с самостоятельной регистрацией
- Если админ создал гостя «Маша 01/01/1985», а потом реальная Маша приходит на сайт и заполняет ту же пару — система авто-входит её в существующий аккаунт (см. §4.1).
- Гость видит свой аккаунт «как будто только что зарегистрировалась», но фактически записи уже были. Это прозрачно.

## 7. Личный кабинет гостя

Структура (вертикальный список разделов):

1. **Профиль** — поля из §3.1, отображение (без редактирования).
2. **Telegram** — статус привязки + кнопки управления (§4.3).
3. **RSVP** — карточка с моим RSVP-статусом на Крестины и Банкет, поле «Со мной придут» (см. `module2-spec.md`, §5).
4. **Информация о мероприятии** — дублируется содержимое модуля 2 (дата, время, адрес, дресс-код, фото/видео и т.д.).
5. **Мои подарки** — список бронирований из модуля 3 с возможностью отменить.
6. **Моя команда** — раздел из модуля 5 (команда в квизе и счёт).
7. **Мини-игра «Ангел Амалия»** — мой накопленный счёт, осталось попыток сегодня, кнопка «Сыграть» (см. `module2-spec.md`, §7).
8. **Кнопка «Выход»** — очищает cookie, возвращает на форму входа.

> Раздел «Мои конкурсы» из ЛК **убран** — гости не взаимодействуют с конкурсами модуля 4 через сайт, всё ведётся ведущим (см. `module4-spec.md`).

Разделы 4–6 наполняются по мере того, как гость взаимодействует с другими модулями. Если в модуле ещё ничего нет — пустое состояние с подсказкой.

### 8.2. Картинки
- **Источник:** кадры из мультфильмов и/или книжные иллюстрации (Союзмультфильм). База подбирается отдельной задачей до старта реализации модуля.
- **Формат:** квадрат ~512×512 px, PNG/JPEG.
- **Стиль:** стараемся подобрать в едином стиле (рисованная анимация Союзмультфильма).
- **Хранение:** Supabase Storage; ссылки на файлы — в БД в таблице `avatars`.

### 8.3. Логика выдачи
- При регистрации нового гостя система получает список свободных героев (`is_taken = false AND reserved_for_admin = false`) и выбирает случайного.
- Один герой = один гость, не повторяется.
- Сменить героя нельзя (даже через админа — только косвенно, через удаление и повторное создание гостя).
- **Котёнок Гав (#49) и Бонифаций (#51)** — оба `reserved_for_admin = true`, исключены из пула гостей.

## 9. Структура БД (черновик)

```sql
guests (
  id uuid pk,
  name text not null,
  birth_date date not null,
  gender enum('M', 'F') not null,
  avatar_id int fk -> avatars(id),
  telegram_id bigint nullable unique,
  telegram_username text nullable,
  created_at timestamp,
  unique(name, birth_date)
)

avatars (
  id int pk,
  name text,                              -- "Чебурашка"
  image_url text,
  is_taken bool default false,            -- занят ли гостем
  reserved_for_admin bool default false   -- true для #49 "Котёнок Гав" и #51 "Бонифаций"
)

telegram_binding_codes (
  code text pk,
  owner_type enum('guest', 'admin') not null,
  owner_id text not null,                 -- guest.id (uuid) или admin.id
  expires_at timestamp,
  used bool default false
)

admin (
  id int pk,
  role enum('mom', 'dad') unique,         -- ровно две строки: мама и папа
  login text unique,
  password_hash text,                     -- argon2
  avatar_id int fk -> avatars(id),        -- мама = "Котёнок Гав" (#49), папа = "Бонифаций" (#51)
  telegram_id bigint nullable,
  telegram_username text nullable
)

sessions (
  token text pk,
  owner_type enum('guest', 'admin') not null,
  owner_id text not null,
  expires_at timestamp                    -- now() + 30 days
)
```

## 10. Технический стек
Наследуется от общего стека проекта:
- **Frontend:** Next.js + Tailwind
- **Backend:** FastAPI (Python)
- **БД:** PostgreSQL на Supabase
- **Хранение картинок:** Supabase Storage
- **Telegram-бот:** aiogram
- **Хэширование пароля админа:** argon2 (через `argon2-cffi`)

## 11. Открытые пункты на этап реализации

- **База картинок героев** — каталог собран и утверждён, 51 финальная картинка готова к загрузке в Supabase Storage (см. `avatars-final.md`).
- **Конкретные параметры формы** (выпадающий календарь, маска ввода ДР) — проектируем при разработке UI.
